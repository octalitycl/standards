## Flujo de trabajo (equipo)

Colaboradores: {{TEAM}}. `main` es la rama de produccion — despliega
automaticamente en cada push a `main`.

**Nada de commits directos a `main` ni a `dev`.** Todo cambio pasa por una
rama y un PR.

```
main                            <- produccion, deploy automatico
└── dev                         <- integracion, preview deploy
    ├── feat/<descripcion>
    ├── fix/<descripcion>
    ├── chore/<descripcion>
    ├── docs/<descripcion>
    └── refactor/<descripcion>
```

Nombre de rama: `^(feat|fix|chore|docs|style|refactor|perf|test|build|ci)\/[a-z0-9._-]+$`.

### Por que existe `dev`

El team de Vercel (Hobby, gratis) no permite invitar members — solo
`{{OWNER}}` es member. Vercel solo genera un deploy si el autor del commit
tiene acceso al team. Por eso, `vercel.json` (`git.deploymentEnabled`)
desactiva el deploy de Vercel para `dev` y para toda rama feat/fix/chore/etc
— Vercel SOLO deploya `main` (produccion).

- Los PRs de feature/fix/etc. se abren contra `dev`, no contra `main`.
- **Merge a `dev`: cualquiera del equipo, con "Create a merge commit"**
  (nunca squash ni rebase — deshabilitados a nivel de repo).
- **Merge a `main` (prod): SOLO `{{OWNER}}`**, via PR `dev` -> `main` con
  "Create a merge commit". Squash-merge conserva el autor original de la
  rama, no el de quien aprieta el boton; el merge commit real si le asigna
  la autoria a quien mergea, que es lo que Vercel necesita ver para no
  bloquear el deploy.

> Nota: repo privado en plan GitHub Free no permite branch protection nativa
> ni Rulesets (403 "Upgrade to GitHub Pro or make this repository public").
> `guard.yml` bloquea push directo a `main`/`dev` y valida las reglas del PR,
> pero **no puede impedir a nivel de Git que otra cuenta con acceso de
> escritura apriete "Merge"** — el job `ownership-audit` lo detecta despues
> del hecho, no antes. Si el repo es publico, o si el equipo pasa a GitHub
> Team, migrar a branch protection/Rulesets nativa.

> **Gotcha verificado:** `delete_branch_on_merge` borra la rama head de
> CUALQUIER PR mergeado — incluida `dev` cuando se usa como head del PR de
> promocion `dev -> main`. Despues de cada promocion, `{{OWNER}}` recrea
> `dev` desde `main` de inmediato:
> `git checkout -B dev origin/main && git push origin dev`.

### Commits — Conventional Commits

`type(scope): mensaje en imperativo`, minusculas, sin punto final, sujeto
<= 50 caracteres. Tipos: `feat`, `fix`, `refactor`, `docs`, `chore`, `style`,
`perf`, `ci`. Sin `Co-authored-by: Claude`, `[AI]`, `Generated by` ni ningun
rastro de autoria de IA. Enforced por `husky`/`commitlint` (hook
`commit-msg`) y por `guard.yml` en el PR.

### Pull Requests

- Titulo: mismas reglas que el commit.
- Descripcion: que cambia + por que + como se probo, usando
  `.github/PULL_REQUEST_TEMPLATE.md`. Minimo 20 caracteres.
- CI (`lint` + `typecheck` + `test` + `build` + `secret-scan`) tiene que
  pasar antes de mergear.
- PR de feature/fix/etc contra `dev`. Promocion `dev` -> `main` solo la
  mergea `{{OWNER}}`.

